Upgrading from PHX 1.x

What to change in code written for PHX 1.x, and what behaves differently now

PHX 1.x ran on the Bullet Physics engine; PHX 2 runs on Jolt Physics. The phx.* classes kept their names and most of their properties, so the greater part of a 1.x script runs unchanged. This page lists what does not:

  • Changes in code — renamed or removed classes, properties and values. Code that uses them stops with an error, so they are easy to find.
  • Changes in behaviour — properties that keep their name but act differently. Code that uses them still runs, but the scene moves differently, so check each item that your scene uses.
  • Scenes saved in PHX 1.x — what a MAT file of 1.x brings back.

Even a scene that needs no change will not repeat a 1.x run to the digit: the contacts, the friction and the joints are solved by a different engine. Constants that were tuned by trial against the old engine — extra damping, controller gains, a very short step that kept a chain together — are worth trying again at their physical values. Checking a ported scene at the end of the page shows how.

An AI coding assistant can do the conversion with the phx-upgrade-from-1x skill that ships with PHX (see AI agent skills): it rewrites the changes in code and lists the changes in behaviour it found, for you to decide.

Changes in code

Engine settings

phx.engine.BulletSettings is replaced by phx.engine.Settings, passed to the simulation as before through its EngineSettings option. For a transition period phx.engine.BulletSettings(Name, Value, ...) still works: it warns (phx:BulletSettings:replaced), carries LengthScale, Margin and MarginMode over, leaves out the other settings and returns phx.engine.Settings; it will be removed in a future release. The function phx.engine.switchEngine is gone.

PHX 1.x (BulletSettings)PHX 2 (Settings)
SolverRemoved; there is one solver. It solves the joints of a group of connected bodies together and directly, which the MLCP solvers ("dantzig", "lemke") were chosen for.
IterationsContactIterations and JointIterations, now caps: the iterations stop when the contacts and joints have converged to ContactTolerance and JointTolerance. PositionIterations is new.
AutoActivatedRemoved; bodies never fall asleep.
LengthScale, Margin, MarginMode (PHX 1.0.16)Unchanged. PenetrationSlop and SpeculativeDistance are new and follow LengthScale in the same way.
—Threads and ContactCache are new.
% PHX 1.x
opt = phx.engine.BulletSettings("Solver", "dantzig", "Iterations", 50, "LengthScale", 0.1);
% PHX 2: leave out the solver and the iterations first; the defaults usually do better
opt = phx.engine.Settings("LengthScale", 0.1);
sim = phx.Simulation(gca, "EngineSettings", opt);

Friction of bodies

phx.Body.Friction was a triplet [drag roll spin]; it is now the Coulomb coefficient alone. Rolling and spinning resistance are two new properties with a different meaning, lengths in metres rather than coefficients:

  • RollingResistance — the arm of the normal force that resists rolling (a torque of up to RollingResistance*N).
  • SpinRadius — the effective radius of the contact patch, which resists spinning about the contact normal by Friction*SpinRadius*N.

Both default to 0 and add up over the two bodies of a contact. A triplet [mu 0 0] is still accepted as mu; a nonzero rolling or spinning value raises the error phx:Body:frictionTriplet, because its 1.x value cannot be carried over. Start without the two new properties and add them only where a body should come to rest that otherwise rolls or spins on: a ball on a flat floor, a spinning coin.

% PHX 1.x
ball = phx.Body("Shape", {"Sphere"}, "Friction", [0.6 0.05 0.01]);
% PHX 2
ball = phx.Body("Shape", {"Sphere"}, "Friction", 0.6, "RollingResistance", 0.002);

The assembly builders phx.assembly.arena, chain, scatter and wall take a scalar Friction too.

Limits of GenericJoint and BushingJoint

The four 1-by-3 properties LowerLinearLimits, UpperLinearLimits, LowerAngularLimits and UpperAngularLimits are replaced by two 3-by-2 matrices, LinearLimits and AngularLimits, with one row [lower upper] per axis X, Y, Z. The old names are not accepted. A free axis is now written as [-Inf Inf]; the 1.x convention lower > upper means free is an error.

AxisPHX 1.x (lower, upper)PHX 2 (row of the matrix)
Locked at vv, v[v v]
Boundeda, b with a < b[a b]
Freeany lower > upper, e.g. 1, −1[-Inf Inf]
% PHX 1.x: rotation about X within +-30 deg, translation along Z free
j = phx.GenericJoint(A, B, "LowerAngularLimits", [-pi/6 0 0], "UpperAngularLimits", [pi/6 0 0], ...
    "LowerLinearLimits", [0 0 1], "UpperLinearLimits", [0 0 -1]);
% PHX 2
j = phx.GenericJoint(A, B, "AngularLimits", [-pi/6 pi/6; 0 0; 0 0], ...
    "LinearLimits", [0 0; 0 0; -Inf Inf]);

The defaults are as before: a GenericJoint is rigid, a BushingJoint free. Angular limits lie within (−π, π), and both are finite unless the axis is free. The meaning of the angles changed too; see Angles of GenericJoint and BushingJoint. A Simulink port that referred to one of the old properties must refer to the new one.

Other renamed or removed names

phx.Resistance EnvironmentVelocity, EnvironmentTwist EnvironmentLinearVelocity, EnvironmentAngularVelocity. The old names still work for now, with the warning phx:Resistance:renamedProperty, and will be removed in a future release. The sense of rotation changed too; see below.
phx.Spring, phx.Rope Colormap as the name of a colormap, e.g. "parula" Colormap as an N-by-3 matrix of colors, e.g. parula(64); empty (the default) draws Color. A name is now an error.
phx.shape.Tube Taper Removed. InnerDiameter takes the bores at both ends, [d1 d2]. A taper t ≥ 0 of a bore d is [d d*(1-t)], a negative one [d*(1+t) d]. When the tube was given its outer Diameter or Radius, the bore was Diameter - 2*WallThickness; give the pair as InnerDiameter alone and leave the outer size out, since a single outer diameter sets a straight bore again.
phx.Simulation RedrawMode "interactive" (the default) Removed; use "adaptive", the new default, or leave the property out.
Engine gateway phx.engine.io phxEngine, with a changed protocol. Code that called the gateway directly has to be rewritten against the phx.* properties, or against the new protocol.

Redraw in a step

The default of the redrawStep argument of step changed from 0 (one redraw at the end of the step) to 1 (redraw whenever useful). In the default "adaptive" mode a redraw is skipped when it would come sooner than one display frame, so sim.step(interval, substeps) now animates the substeps of a long step at the speed of the display. Pass 0 to keep the 1.x behaviour, and -1 for a headless run as before.

Changes in behaviour

Applied forces and torques persist

AppliedForce and AppliedTorque of phx.Body acted for one step in 1.x, so a script assigned them before each step. They now act in every step until they are changed. A script that assigns them before each step works as before; a script that assigned a force once, for a single push, now pushes for ever. Use applyForce and applyTorque for a load that acts for one step, or set the property back to [0 0 0].

body.AppliedForce = [0 0 50];      % acts from now on, until changed
body.applyForce([0 0 50]);         % acts in the next engine step only

AppliedTorque of phx.RevoluteJoint and AppliedForce of phx.PrismaticJoint were driven through the motor in 1.x: a nonzero value replaced TargetVelocity and MaxTorque (MaxForce). They are now loads of their own that act together with the motor. A joint that has both a motor with nonzero MaxTorque and an applied torque now gets the sum: the motor works against the applied torque to keep its target velocity. Set MaxTorque to 0 where the applied torque should act alone.

Centre of mass of cones and mesh-based shapes

Every body in 1.x had its centre of mass at the origin of its frame. A body now has a CenterOfMass given by its shape, about which it turns and at which gravity acts. For a box, sphere, cylinder, capsule, rock and terrain it is still the origin, but it moved for:

  • phx.shape.Cone — on its axis, a quarter of the height above the base, where a solid cone has it;
  • phx.shape.Mesh, Extrusion, Revolution and Tube — at the centroid of the mesh, with Inertia about it.

A mesh whose origin lies away from its centroid, a part exported from CAD in assembly coordinates for example, therefore swings and tips as the real part would, no longer about its origin. Position and Orientation still give the body frame. A body that should turn about its origin as in 1.x gets CenterOfMass [0 0 0]; its Inertia stays as the shape gave it.

The mass of a Revolution whose profile ends off the axis without returning to its first point is now that of the solid closed to the axis; in 1.x it depended on where the origin lay.

Springs and ropes are solved by the engine

phx.Spring and phx.Rope computed their force in MATLAB in 1.x, from the positions of the previous step, and applied it as an external force. The engine now solves them with the joints and contacts, by an implicit scheme that keeps their energy and is stable at any stiffness and damping. A stiff spring that needed a very short step, or extra damping, to stay stable runs at an ordinary step now; and a spring that was stable only thanks to the numerical damping of the old scheme is now damped by its Damping alone. Use the physical values of stiffness and damping and check the step: a spring that oscillates faster than about one radian per substep (ω·dt > 1) stays stable but moves inaccurately.

Joints hold tighter

The joints of a group of connected bodies are solved together and directly, closed loops included, so chains, linkages and loaded mechanisms stretch far less at ordinary steps. The 1.x remedies — a direct MLCP solver, many iterations, a very short step, extra damping at the joints — are not needed and cost time; remove them and check the result. The joint motors keep their meaning (TargetVelocity with MaxTorque or MaxForce).

The joint reactions ForceA, TorqueA, ForceB and TorqueB are exact for all joint types. In 1.x the TorqueA of a revolute joint attached to a static or kinematic body missed the bending moment the joint carries, so a measured value may differ from the one of 1.x.

Angles of GenericJoint and BushingJoint

The angular limits of 1.x bounded three successive rotations about X, Y and Z, and the rotation about Y degenerated near ±90°. The rotation is now split into a twist about the Z axis of the joint frame and a swing about X and Y, each limited separately; there is no singularity at 90°. A joint that rotates about one axis only behaves as before. When several axes rotate at once, leave the freest rotation to Z (the twist): the 1.x advice to keep a free axis on X or Z and lock Y no longer applies. The limits, and the springs of a BushingJoint, can now be changed while the simulation runs; in 1.x they were read only when it was built.

Rotating environment of Resistance

The environment of phx.Resistance rotated against the right-hand rule in 1.x. Its velocity at a point p is now EnvironmentLinearVelocity + cross(EnvironmentAngularVelocity, p - EnvironmentOrigin), so a positive z component turns it counter-clockwise seen from above. To keep the motion of a 1.x scene, negate the value that was assigned to EnvironmentTwist.

Contacts and friction

  • The contacts are solved more accurately: stacks stand at longer steps, sliding friction holds its Coulomb value at any speed, and bodies sink less into each other. Scenes whose outcome depends on a contact (a toppling stack, a gripper holding a part, a wheel on a slope) may end differently than in 1.x.
  • Rolling and spinning resistance are defined anew (see Friction of bodies).
  • Bodies never fall asleep: a body at rest is simulated like any other, and nothing has to wake it when something touches it.
  • The pose of a kinematic body that is set once before step(interval, substeps) with several substeps is reached in the first substep, and the body stands still in the others. Set the pose before every step without substeps, or drive a kinematic body by its LinearVelocity and AngularVelocity, which hold until changed.
  • applyForce and applyTorque with several rows apply each row as a force (torque) of its own. In 1.x several rows at once gave a wrong resultant.

Scenes saved in PHX 1.x

A MAT file saved in 1.x loads in PHX 2 and simulates, and each body keeps the centre of mass and inertia it was saved with, so a saved mesh keeps turning about its origin. Values that changed their form are converted: a single Diameter of a cone loads as [d 0], a single InnerDiameter of a tube as [d d], a friction triplet [mu 0 0] as mu. What has no counterpart is left at its default, without a warning:

  • the limits of a GenericJoint (it loads rigid) and of a BushingJoint (it loads free);
  • a Friction with a nonzero rolling or spinning part (it loads as 0.5);
  • the Taper of a tube (it loads straight);
  • a colormap name of a spring or rope (it loads drawn in its Color).

Set these again after loading, or better rebuild the scene with the script that made it and save it anew. The same holds for the MAT scenes of a PHX Model block in Simulink.

Checking a ported scene

  1. Run the scene and fix the errors from Changes in code.
  2. Go through Changes in behaviour for the properties the scene uses, above all AppliedForce/AppliedTorque and meshes off their origin.
  3. Remove the engine workarounds of 1.x — solver choice, raised iterations, artificial damping, a step much shorter than the table in Units, scale and engine settings recommends — and run again.
  4. Switch on the accuracy diagnostics, which report joints and contacts that did not converge, deep penetrations, open joints and too fast bodies, naming the objects and the remedy: 
    sim.DiagnosticInfo = "warnings";
sim.step(5, 1000, -1);
getDiagnosticReport(sim)
  5. Check a result that matters by halving the substep: if it changes, the step was too long.
New in PHX 2. Besides the changes above, PHX 2 adds deformable and granular objects (phx.SoftBody, phx.FlexibleBody, phx.Particles), the torsion spring phx.TorsionSpring, end stops of all joints (Limits, ConeAngle, TwistLimits), Inertance of springs, truncated cones, body accelerations, a multithreaded engine step and the accuracy diagnostics.
