phx.Simulation

Scene root that steps the physics engine

Class  phx.Simulation  |  Superclass: phx.base.Object

Description

phx.Simulation is the topmost object in the hierarchy of a physical scene. It collects a set of phx.Body objects together with all of their children (joints, springs, force elements, traces, loggers…), builds the execution pipelines that advance and render them, and steps the underlying physics engine forward in time.

Adding or removing objects requires a rebuild of the simulation pipeline. This operation is done automatically, but may take a while.

Deleting a simulation object disconnects the engine, but if the visualization window is open, the model objects themselves remain and the simulation object can be recreated.

Creation

Syntax

sim = phx.Simulation sim = phx.Simulation(bodies) sim = phx.Simulation(___,Name,Value)

Description

sim = phx.Simulation creates a simulation of all bodies found in the current axes (gca) and their children.

sim = phx.Simulation(bodies) creates a simulation of the given bodies and their children. bodies may be a phx.Body array or cell array, an axes object, the name of a MAT file, or a struct of bodies.

Pass [] only through one of the explicit sources; an axes handle is the usual choice.

sim = phx.Simulation(___,Name,Value) sets properties using one or more name-value arguments, for example phx.Simulation(bodies,"Gravity",[0 0 0]).

bodiesphx.Body | cell | axes | char/string | struct Source of the bodies to simulate. An axes (or UIAxes) collects every body drawn into it; a char/string is treated as a MAT file to load; a struct is scanned for its phx.Body fields.

Redraw modes

RedrawMode controls how the figure is refreshed during step and, in the adaptive mode, also how often. The other modes redraw on every substep that the redrawStep argument of step asks for. Only the drawing changes with the mode; the simulation itself, and so its results, are the same in all of them.

ValueFramesDescription
"adaptive"as the renderer allows Default. A requested redraw is skipped when it would come sooner than one display frame (1/60 s) after the previous one, or sooner than twice the time the previous redraw took, so the drawing never takes more than about half of the run. While the simulation runs ahead of real time, a frame is still drawn at least every FrameSpacing seconds of simulation time, so a light scene is seen moving instead of jumping to its end. The graphics are brought up to date at the end of every step, and UI callbacks are serviced after each redraw, so the scene can be orbited, zoomed and picked and the buttons of an app or of phx.extra.Viewer keep responding.
"full"every redrawStep Every requested redraw is drawn with drawnow, which waits until the figure shows it, and callbacks are serviced. The slowest mode; choose it when every frame matters, for example when recording a video with phx.Camera.
"performance"every redrawStep Every requested redraw is sent to the screen without waiting and without servicing the callback queue, so the figure does not react to the mouse or the keyboard while a step is running. The cost of drawing is the lowest per frame and the most predictable, which suits benchmarks and timing measurements.
"none"— No screen update at all. The graphics objects themselves are still updated, so the figure catches up once MATLAB becomes idle again.

A simulation that is much faster than real time, such as an orbit followed over thousands of seconds, would draw more frames than it needs with the default FrameSpacing; set it to the time scale of the motion, for example phx.Simulation(bodies,"FrameSpacing",1) for one frame per simulated second. To see a light scene in real time instead, set PacingRate.

Note. A redraw that services callbacks is a re-entrancy point: with "adaptive" or "full", user callbacks can run in the middle of step. Do not delete the simulation or its bodies from such a callback. For runs that need no picture at all, suppress rendering in step (redrawStep of -1) rather than setting RedrawMode to "none": "none" skips only the screen update, while the graphics are still brought up to date on every requested redraw — on a 200-body scene that is several times the cost of a genuinely headless step.

Pacing

By default step runs as fast as the computer allows. PacingRate sets an upper limit on the speed of the run instead: the simulation waits whenever it gets ahead of real time multiplied by PacingRate.

sim = phx.Simulation(ax, "PacingRate", 1);   % at most real time
sim.step(5, 500);

The wait happens at each requested redraw (in the adaptive mode also at one that is skipped) and at the end of each step, so the code between two calls of step in a loop counts towards the real time as well. A single long step that does not redraw (redrawStep of 0 or -1) runs at full speed and waits only at its end.

Pacing only slows a run down. A delay of up to 0.1 s is made up by the following steps, so the short oversleeps of pause do not add up. A scene that cannot keep up runs as fast as it can, and after a longer slow moment (a heavy frame, a breakpoint, a pause between two calls) it continues from there at the set rate rather than speeding up to catch up. Setting PacingRate starts the timing afresh.

Note. The wait is done with pause, which services the callback queue and refreshes the figure. With "performance" or "none" redraw modes the figure therefore reacts and updates during the waits. On Windows a wait of a few milliseconds can last up to about 16 ms. Pacing has no effect while pause is turned off by pause("off").

Diagnostics

A scene can run without an error and still be wrong: joints that stretch, bodies that sink into each other or pass through a wall. DiagnosticInfo makes the engine report after every call of step how well it solved the scene, and warns when a result looks untrustworthy. Use it when a scene behaves strangely, and to check the time step and the solver settings of a scene that matters.

ValueDescription
"off" Default. Nothing is collected and the run costs nothing extra.
"warnings" A warning when a limit below is exceeded, each kind once per simulation. The numbers are available from getDiagnosticReport; nothing else is printed.
"summary" The warnings, and one line in the Command Window per call of step.
"detailed" The warnings, and a few lines per call of step that also name the bodies and joints concerned.
sim = phx.Simulation(ax, "DiagnosticInfo", "detailed");
sim.step(0.05, 5);
PHX diagnostics at t = 0.05 s: 5 steps, engine 0.0505 ms per step (longest 0.0973), 9 active bodies
  solver:      2 islands per step (0 split), 19 iterations per island (most 24)
  residual:    joints 0.00098 (0 islands at the cap), contacts 0.061 (5 islands at the cap)
  penetration: 0.136 mm, phx.Body at [-2.09e-05 2 0.3] and phx.Body at [-6.4e-05 2 0.5]
  joint gap:   0.00267 mm, phx.RevoluteJoint of phx.Body "link1" and phx.Body "link2"
  fastest:     0.544 m/s, phx.Body "link2"; 2.15 rad/s, phx.Body "link1"

Each line covers the engine steps of one call of step, taking the worst value over them. Bodies are named by their Name, or by their class and position; joints by their class and the bodies they connect.

  • solver — the bodies that touch or are joined form islands, each solved on its own; an island of many bodies is split to be solved on several threads. An island stops iterating when its joints and contacts meet JointTolerance and ContactTolerance of phx.engine.Settings, at the latest at JointIterations or ContactIterations (its cap); the islands that reached their cap without meeting their tolerances are counted apart for islands with joints and islands of contacts only, so that it shows which cap to raise. Heaps of bodies rarely converge and reach their cap as a rule; the depth of their contacts (penetration below) tells whether that matters.
  • residual — how far the solver still was from a solution after its last iteration: the largest change of velocity that one joint or one contact still made to a body in that iteration, as a fraction of what the joints and contacts changed that body's velocity in the step (at least |g|·dt). It is the quantity of the tolerances: a residual at or below the tolerance means a converged island, one above it an island stopped by its cap. The residuals have no warning: a scene that fails shows it in its joint gaps and penetrations, while joints held against the limit of a motor or against friction keep a residual that neither more iterations nor a shorter step remove.
  • penetration — the deepest overlap of two bodies in contact.
  • joint gap — the widest separation of the two halves of a fixed, revolute or spherical joint, or across the axis of a cylindrical joint.
  • fastest — the highest linear and angular speed of a dynamic body.

The warnings and their limits, with lengths relative to the LengthScale of phx.engine.Settings:

IdentifierWarns whenUsual remedy
phx:Simulation:nonfinitea body reached a NaN or Inf pose or velocity The simulation has failed; reduce the step.
phx:Simulation:initialOverlapin the first step of a new or changed scene (after creating the simulation or addObjects), bodies are inside each other by more than 10 % of LengthScale Place the bodies apart. The engine pushes them out over the first steps, often violently; deepPenetration stays silent until it has done so.
phx:Simulation:deepPenetrationlater, bodies sink into each other by more than 10 % of LengthScale (rigid contacts; a compliant contact sinks by design, see CompliantPenetration) Reduce the step; check LengthScale and the mass ratios.
phx:Simulation:jointGapa joint is pulled apart by more than 5 % of LengthScale Reduce the step, or raise JointIterations.
phx:Simulation:fastBodya body moves more than half of LengthScale in one engine step Reduce the step: from about one LengthScale per step a body passes through thin parts.

The warnings are ordinary MATLAB warnings, printed without a backtrace. Turn one off with warning("off","phx:Simulation:fastBody"), for example for a body that falls freely and touches nothing. Changing DiagnosticInfo lets every kind warn once more. A warning is a hint, not a proof: a parcel that falls off a conveyor and keeps falling triggers fastBody although nothing is wrong.

Note. Collecting the diagnostics adds a few per cent to the time of the engine step and does not change the results. Leave DiagnosticInfo off for production runs and for timing measurements.

step

step(sim,interval) step(sim,interval,substeps) step(sim,interval,substeps,redrawStep)

Advances the simulation by interval seconds. With substeps the interval is divided into that many engine steps of size interval/substeps; smaller substeps improve the stability of stiff constraint networks. redrawStep (default 1) requests a redraw on every redrawStep-th substep. The adaptive redraw mode treats any positive value alike and redraws as often as the renderer allows; the full and performance modes redraw exactly on the requested substeps. With 0 the view is not redrawn, the graphics are only brought up to date at the end of the step; with -1 the graphics are not touched at all (headless runs). The way and frequency of redrawing are set by the RedrawMode property; the speed of the run can be limited by the PacingRate property.

addObjects

objs = addObjects(sim,axes) objs = addObjects(sim,fileName) objs = addObjects(sim,bodies)

Adds top-level objects, such as bodies, with all their children to a running simulation and rebuilds the pipelines, then returns the added objects in a cell array for further manipulation. A top-level object is one that no other object owns: a joint, a spring or a logger comes along with the bodies it belongs to and cannot be added on its own. From axes and from a MAT file only the top-level objects are taken; anything else stored there is left out.

getDiagnosticReport

report = getDiagnosticReport(sim)

Returns the numbers that DiagnosticInfo collected during the last call of step, as a struct. It is empty while DiagnosticInfo is "off" and before the first step. Use it to check the accuracy of a run in a script, without reading the Command Window.

FieldDescription
TimeSimulation time at the end of the call, s.
StepsNumber of engine steps in the call.
StepTime, MaxStepTimeMean and longest wall time of one engine step, s.
ActiveBodiesNumber of bodies the engine moves.
Islands, SplitIslandsIslands per engine step, and how many of them were split to be solved on several threads.
Iterations, MaxIterationsVelocity iterations per island, mean and most.
JointIslandsAtCap, ContactIslandsAtCapNumber of islands that ran to their cap without meeting their tolerances, summed over the steps: islands holding a joint, spring or rope (cap JointIterations; ContactIterations for springs and ropes alone), and islands of contacts only (cap ContactIterations).
JointResidual, ContactResidualLargest relative residual of a joint and of a contact (see Diagnostics); NaN when there were none.
Penetration, PenetratingBodiesDeepest penetration of a rigid contact, m, and a cell array of the two bodies concerned.
CompliantPenetration, CompliantBodiesDeepest penetration of a compliant contact (ContactStiffness), m, and its two bodies: the deflection of its spring, F/k. It is the contact law, not an error, so no warning looks at it.
JointGap, GapJointWidest joint gap, m, and the joint concerned (in a cell array).

MaxAngularSpeed, FastestTurningBodyHighest angular speed, rad/s, and the body.

WarningsString array of the identifiers of the limits exceeded in this call, also of those not printed again.

The objects in the cell arrays are the phx.* objects of the scene, so they can be inspected or changed directly.

findTopLevel

objs = phx.Simulation.findTopLevel(ax)

Static method that returns a row cell array of the valid top-level objects, such as phx.Body objects, drawn directly in the axes ax, in the order of ax.Children (the most recently created first). These are the objects that addObjects takes from axes. The objects attached to them, such as joints, are reached through their Children. Use it to save the scene shown in an axes, see Saving and Loading Scenes.

Examples

Step a minimal scene

clf; view(3); axis equal; grid on; camlight headlight;

phx.Body("Position", [0.6 -0.5 2]);   % dynamic body
phx.Body("Type", "static");             % ground

sim = phx.Simulation;                  % all bodies in the current axes
sim.step(1, 100);                      % 1 s in 100 substeps

Custom gravity and engine settings

% Zero gravity; a large scene stepped on four threads
sim = phx.Simulation(gca, "Gravity", [0 0 0], "EngineSettings", ...
    phx.engine.Settings("Threads", 4));
sim.step(4, 800, -1);                  % run headless (no redraw)

Add and delete objects between steps

sim = phx.Simulation(boxes, "HideInvalid", true);
sim.step(5, 500);

sim.addObjects(newBox);                % rebuilds pipelines
sim.step(10, 1000);

delete(boxes(7));                      % also triggers a rebuild
sim.step(5, 500);
delete(sim);                           % tear down the engine world

Check the accuracy of a run

sim = phx.Simulation(ax, "DiagnosticInfo", "warnings");
worst = 0;
for k = 1:100
    sim.step(0.02, 4, -1);             % 5 ms engine steps, headless
    r = sim.getDiagnosticReport;
    worst = max(worst, r.JointGap);
end
fprintf("widest joint gap %.3g mm\n", 1000*worst);
